# ADR 0012: The HTML report and `explain` (Milestone 6)

- Status: accepted (Milestone 6)
- Date: 2026-11-08

## Context

PRD US-005 asks for a shareable, self-contained HTML report with a summary, ranked findings, filters, a light/dark toggle, and (i) buttons that reveal the longer explanation. `docs/DESIGN.md` defines it on the brand's IBM Carbon standard: load the brand's stylesheets and classes, never name a color or a font, and make it accessible to WCAG 2.2 AA. The roadmap also asks for `explain` polish.

## Decisions

### One file, built from the brand's own sheets
`siftcode scan --format html` produces a single file: the brand's stylesheets (in the order its guide gives: theme, fonts, tokens, base, components, layout), the report's own rules, both brand fonts embedded as data URIs, the brand's icon sprite, the mark and wordmarks, and one script. Nothing is fetched.

- **Where the brand lives.** `assets/brand/` is the brand's application set, generated by `brandkit bundle siftcode assets/brand` and verified by `brandkit check siftcode assets/brand` (kit 1.56.1 at the time of writing). It is not edited by hand; Prettier and ESLint skip it. The report's own `assets/report/report.css` and `report.js` hold only what the brand does not provide. They use brand tokens and classes only (no hex, no `font-family`). The package ships exactly the files the report reads (`package.json` `files`; checked with `npm pack --dry-run`), plus the two font licenses.
- **Read at run time, not generated code.** `src/reporters/html/assets.ts` reads the files once per process (the same approach as `data/licenses`), strips CSS comments, rewrites each `url(../font/x.woff)` into a data URI, and normalizes line endings so hashes do not depend on how the package was installed.
- **Deterministic and shareable.** No timestamps, and only the scanned folder's name, never its absolute path, so the same scan gives the same bytes (an existing test over every format enforces this).

### Security: a strict content policy and escaping
The page carries a `Content-Security-Policy` of `default-src 'none'`, scripts only by SHA-256 of its two inline scripts (so markup injected through a file name or a message cannot add a third), images and fonts only from `data:`, and no form or base URI. All text from the scanned code goes through `esc()`; links to standards must be `http(s)` URLs (`safeUrl`), open in a new tab with `rel="noopener noreferrer"`, and say so for screen readers; there are no inline event handlers. `style-src` keeps `'unsafe-inline'` because the brand's icon sprite carries a `style` attribute; the risk is limited because every dynamic value is escaped and scripts are pinned. Tests cover each of these.

### Findings are plain HTML; the script only adds behavior
The findings are server-rendered `<details>` elements, so the report reads, expands, and prints with JavaScript off. The script adds the light/dark toggle (system preference by default, choice kept in `localStorage` with a safe fallback, applied before first paint by a tiny head script so a saved dark choice does not flash light), the (i) buttons (real buttons with `aria-expanded` and `aria-controls`; Enter opens one, tested, and Escape closes it and returns focus), the filters (severity chips, category, language, rule, and a search box that `/` focuses; a live count and a designed "nothing matches" state), expand and collapse all, copy buttons for the before and after examples (the browser's clipboard API with the older selection method as a fallback, and a spoken "Copied" or "Copy failed"), and opening a finding from a link (the hotspot list). The script has no automated tests (TD-21); it was exercised in a browser.

### What the report shows
Header with the brand lockup and theme toggle; a "clean" state or severity counts (error, warning, info, note, each a word plus an icon, with an edge on the row as a second cue); the top three hotspots from `SC-HOT-001`; banners for files that were not checked and for the scan notes; filters; findings grouped by file with the most severe file first (the same order as the terminal report); a table of accepted findings with how and why (ADR 0011); an "About this report" section with the rules that ran and the limits of syntax-only analysis. Project-wide findings are labelled "Whole project" rather than `.`.

### `explain`
`siftcode explain` with no id lists every rule by category with its default severity. An id may be written loosely (`met-1`, `sc-met-01`). A mistyped id names the closest rule instead of printing all 39. An explanation now also shows the rule's default options (read from its own schema), how to change its severity or switch it off, and how to accept a finding: a `siftcode-ignore` comment for a file-level rule, or the baseline for a rule about the project as a whole (which has no line to comment on).

## Evidence

Checked in the built-in browser on a real C# report (FluentValidation, 94 findings in 83 files, 642 KB) at 375, 768, and 1280 px:
- No horizontal overflow at any width (measured), no console errors, fonts loaded from the embedded data.
- **Contrast** (every visible text node, 2,405, with every row and panel open, in both themes, transitions disabled): zero below 4.5:1 for small text or 3:1 for large. The first run found two real shortfalls in brand pairs, both fixed in `report.css`: the muted label on a card in the dark theme (4.19:1) and a ghost button's text on its hover wash in the light theme (4.14:1). Two further "failures" in that run were artifacts of measuring while the hidden browser pane had frozen a color transition, and are not findings.
- **Structure:** one `h1` and no skipped heading level; one each of header, main, footer, and search landmarks; every control named; no duplicate ids; every `aria-controls` resolves; no remote reference; no inline handler; no target under 24 px.
- **Keyboard:** Tab order is skip link, brand, theme toggle, info buttons, and on; every focused element has a visible 2 px outline; Enter opens an explanation and Escape closes it with focus on its button; `/` focuses the search.
- **Behavior:** a severity chip filtered 94 findings to 72 and hid empty file groups; a search for "lockfile" found exactly the 5 findings about lockfiles; clearing restored all; the theme choice survived a reload; a real click on Copy gave "Copied".
- **Not done:** an automated accessibility engine such as axe-core was not run (it is not installed and the check must work offline); the audit above is a script written for this milestone. A screen reader was not used.

## Consequences

- The report is about 290 KB for a clean project and grows by about 4 KB per finding. Most of the fixed part is the two embedded fonts.
- The brand's stylesheets are used as they are. When the brand is rebuilt, run `brandkit bundle` and `brandkit check`, regenerate a sample report, and re-run the contrast check: the report's overrides depend on the brand's token values.
- `assets/` sits beside `dist/`, so the built CLI finds it only inside the package or the repository (the end-to-end test covers this).
