# SiftCode

A product. Its initials are **SC**.

Generated by brandkit 1.56.1 on 2026-11-06, from the
same build that wrote the files it names. **Do not edit it** - the next build
overwrites it, and that is the point: it cannot name a file that is not there

Point a person or an agent at this file and nothing else. It names the file for

Every path below is relative to this folder.

## Type

This brand is **named** in **JetBrains Mono**, at 200, 800, and **read** in **Public Sans**.

- `--font-display` is JetBrains Mono: the wordmark, the headings, the initials in an avatar.
- `--font` is Public Sans: body copy, labels, the text in a table.
- `--mono` is JetBrains Mono, for code and columns of figures.
- Link `template/fonts.css`, which declares every face this brand uses and points at the files in `font/`.

Load the sheet and use the tokens rather than naming a family in your own CSS. Which face does which job is a decision recorded in the brand's definition, and an application that writes `font-family` itself is a second place that decision lives - and the place it will be wrong, because the display face is drawn to be a logo and not to be a paragraph.

Letterspacing for the name itself is `+0.000em`. That is for the wordmark, which is already drawn - it is here so that type set to match the logo can be set to match it.

## Colour

**Do not write a colour into an application.** Load one of these and every screen moves when the brand moves:

- `template/tokens.css` - the roles as CSS custom properties, light and dark
- `theme/theme.css` - the same thing standalone, for a project with no page shell of ours
- `theme/theme.json` - the same values as data, plus every contrast ratio this build measured

`brandkit doctor` measures every pair that gets read and says which clear WCAG and by how much. A note there is not a failure: it is usually a pale brand fill, which is fine behind text and invisible as a hairline.

## The file for each job

### The browser tab

`web/head.html`

Paste the whole block. **Do not add icon links beside it.** A browser handed several picks one by rules of its own rather than by the order they are written in - Chrome takes the `.ico` - so a list is not a preference, it is a lottery. The block offers exactly one, with a version on the URL, because a favicon is cached on its URL and a browser holds one well past `no-cache`.

### The top left of a screen

`template/header.html`

The symbol on a tile in the brand's own colour, with the wordmark beside it. Use the `logo`-coloured tile, not the `page`-coloured one: the page colour is near-white and never changes with the theme, so on a dark header it reads as a white box around the symbol.

### The bottom of a screen

`template/footer.html`

The legal line and the address. The company in the copyright is already a link to its own site.

### A home screen or an installed app

`web/site.webmanifest`

Already names the right icons at the right sizes. The maskable ones are separate and are not interchangeable with the plain ones: Android crops to whatever shape the launcher likes and only guarantees the middle 80%.

### A link preview

`social/`

The Open Graph tags in `web/head.html` already point at the image.

### An avatar or an upload form

`icon/`

The `avatar-*` exports are built under a megabyte, which is what GitHub and most other forms refuse above - usually without saying so until the file is already chosen.

### One colour, or somewhere colour will not survive

`wordmark/`

The `mono-black` and `mono-white` cuts. A fax, an embroiderer, a single-colour print, somebody else's slide.

### Icons inside the application

`ui/`

One set, drawn to one grid and one stroke weight, so they look like each other. Mixing in an icon from elsewhere is visible immediately.

### The top of a repository's README

`lockup/banner/lockup-horizontal-light-banner.png`  
`lockup/banner/lockup-horizontal-dark-banner.png`

**Both, in that order.** GitHub draws a README on a white page or on a near-black one to suit whoever is reading, and these exports are transparent, so one on its own is a logo that half your readers never see. `<picture>` is how a README asks for the pair:

```html
<p align="center">
  <picture>
    <source media="(prefers-color-scheme: dark)"
            srcset="docs/brand/lockup/banner/lockup-horizontal-dark-banner.png">
    <img alt="SiftCode" width="480"
         src="docs/brand/lockup/banner/lockup-horizontal-light-banner.png">
  </picture>
</p>
```

**`align="center"` on the paragraph, not CSS.** The art is already centred inside the image, with equal clear space on all four sides, but GitHub left-aligns an image like any other inline content - so without the wrapper a 480-pixel logo sits against the left margin of a 900-pixel column and reads as though it slipped. GitHub's Markdown strips `style` attributes, so a `text-align` that centres it in a local preview does nothing on the page itself; the legacy `align` attribute is the one it honours.

`docs/brand/` is wherever you put them - see below. **The banner cut, not its neighbours.** It is 3:1 with the clear space already in it, which is the shape a strip across the top of a page wants; the `wide/` cut beside it is 16:9 and the `square/` one is 1:1, and a README image is scaled to the column width, so either of those is most of a screen of nothing before the first line of prose. Not the link-preview image in `social/` either: that one carries its own background on purpose, which on a dark README is a pale slab with a logo in it. **PNG, not the SVG beside it** - GitHub serves a README's images through a proxy that sanitises SVG, so a vector that renders perfectly here can arrive there as nothing at all.

## The design standard

This brand's interface is built to **IBM Carbon** (IBM), and to nothing else. https://carbondesignsystem.com

It sets the shape, spacing, elevation, type scale and motion in `tokens.css` and how a control looks and behaves in `components.css` and `layout.css`. The colours, the mark and the display face stay this brand's own. Build new screens to the standard, and do not mix in another one's patterns: two standards on one product is two answers to every button.

What it asks, as this kit applies it:

- Corners are square: a button, a field, a card and a menu have none; only a tag, a toggle and a circle are round.
- Space comes from the scale 2, 4, 8, 12, 16, 24, 32, 40, 48, 64, 80, 96 and 160; sizes are multiples of the 8 px mini unit.
- A control is 32, 40 or 48 px high, and a button and a field default to 40 so one beside the other lines up.
- A text-only button sits 16 px from its label on the left and 64 on the right; an icon goes at the far end.
- A field is filled, with a 1 px rule along the bottom and no other edge; focus is a 2 px outline inside the box.
- Depth is background tone: the page, then layer-01, 02 and 03, and a field takes the layer it sits on - not a shadow.
- Only what floats casts a shadow - a menu, a toast - and it is one shadow, 0 2px 6px; a modal sits on its scrim and casts none.
- Text is in the productive type scale, regular weight, with semibold only for the two smallest headings and for a selected tab.
- Nothing is set in capitals; a label is sentence case, 12 px, in the quiet text colour.
- A selection is a tint with a 3 px stripe on its edge; a hover is a 12% neutral wash (16% on dark).
- A tag is a 24 px pill; an inline notification has a 3 px stripe on its near edge and nothing else.
- Motion is 110 ms for a state change and 240 ms for movement, on the standard curve, with an entrance curve for what appears.
- The shell is 48 px of header with a 1 px rule under it, and a 256 px side nav whose links are 32 px high.

IBM Carbon was drawn around IBM Plex Sans; this brand reads in Public Sans instead, which is allowed.

## The things that are easy to get wrong

Each of these has gone wrong at least once in something built from this kit. They are here rather than in a comment in a file somebody may not open.

1. **One icon link in the `<head>`, with a version on it.** Several links is a lottery the browser draws, and a favicon without a changing URL is cached past the fix.
2. **The tile at the top left is the `logo`-coloured icon**, not the `page`-coloured one. The page colour is near-white and fixed, so it reads as a white box on a dark header.
3. **Never retype a colour.** Load the tokens. A hex in an application is a second place the brand is written down, and the two drift silently.
4. **Never name the typeface yourself.** Link the font sheet, for the same reason.
5. **The light/dark image pair** is switched by `.bk-only-light` and `.bk-only-dark`, and nothing else may set `display` on an element carrying one. A heavier selector elsewhere silently shows both.
6. **Plain icons and maskable icons are not interchangeable.** The maskable ones are drawn small inside a filled square because a launcher crops them.
7. **Copy the files, do not link into this folder.** This directory is generated output and every build rewrites it.
8. **A README header is a pair, not a file.** One image means half the people who open the repository see a gap where a logo was: GitHub picks the page colour to suit the reader and these exports are transparent. Take both and let `<picture>` choose.

## Taking this into a project

Do not copy by hand. Two commands:

```
brandkit bundle siftcode path/to/your/project/static/brand
brandkit check  siftcode path/to/your/project/static/brand
```

The first writes the 42 files an application needs, in the folder shape they have here. The second says what has happened to that copy since: what is missing, what somebody edited in place, and what is in there that this brand never contained.

**A repository is not an application.** A command-line tool has no screen, and a `static/brand` folder of stylesheets, fonts and maskable icons in a project that has no `static/` is a set nobody will keep in step - so there is a second, named set, and it is exactly what the README job above names:

```
brandkit bundle siftcode path/to/your/project/docs/brand --set readme
brandkit check  siftcode path/to/your/project/docs/brand --set readme
```

Same shape, same hashes, same `check`. Put them wherever the repository keeps its pictures and point the `<picture>` block at that folder; the files keep the path they have here, which is what lets `check` find them again.

**The folder names are part of it.** Every stylesheet and partial in `template/` refers to its neighbours as `../font/`, `../mark/` and `../wordmark/`. A copy that flattens them into one directory is a copy they cannot find their way around, and it is also a copy nothing written here describes - which is how two applications built from one brand end up with two layouts and no way to compare them.

**Re-run `bundle` when the brand changes rather than editing in place.** These are generated files. An edit here is lost at the next build; an edit there is a brand that has quietly forked, and `check` will say so.

`BUNDLE.json` beside this file lists exactly what is in each set, with a hash of every file, which is what `check` compares against.
