SiftCode scans a software project and finds places where it departs from proven standards:
complexity metrics, design principles, security weaknesses, supply-chain hygiene, licensing, and
missing design documentation. For each finding it names the standard behind it and suggests a
concrete improvement. It runs offline, and it parses your code without ever running it.

> **Status: early development (Milestone 7).** The engine, configuration, and report formats
> (terminal, JSON, Markdown, SARIF, HTML) work, with 56 rules for JavaScript/TypeScript, Python, and C#:
> six code metrics, two architecture checks, six accessibility checks for JSX, five design heuristics, seven security checks, seven supply-chain checks,
> eight design-documentation checks (two of them compare diagrams with the code), eight license checks, three testing-readiness checks, three
> resilience checks, and a hotspot ranking. See the [roadmap](docs/ROADMAP.md); the first release is
> prepared in [docs/RELEASING.md](docs/RELEASING.md).

## Quick start

Requires Node 24 or newer.

```bash
git clone https://github.com/BlackCanyonSoftware/siftcode_BCS.git
cd siftcode_BCS
npm ci
npm run build
node dist/cli/main.js scan path/to/your/project
```

Example output:

```text
SiftCode scan: /home/you/project
Scanned 12 files
  JavaScript  4
  TypeScript  8

Findings: 1 (0 error, 0 warning, 1 info, 0 note)

src/billing.ts
  src/billing.ts:14  info  SC-MET-001  Function "processOrder" is 72 lines long (limit 50).
      Why: Long functions are harder to read, test, and change, and they usually do several jobs at once.
      Try: Extract cohesive blocks into small, well-named functions so each one does a single job.
      Standard: Refactoring (Fowler): Extract Function (https://refactoring.com/catalog/extractFunction.html)

Skipped: 3 unsupported, 0 too large, 0 symbolic links
```

## Commands

```text
siftcode scan <path> [options]     scan a folder or file
siftcode baseline <path>           accept the current findings, so later scans report only new ones
siftcode explain [rule-id]         why a rule exists, the standards behind it, how to fix it (no id: list the rules)

  -f, --format <name>     text (default), json, markdown, sarif, or html
  -o, --output <file>     write the report to a file instead of printing it
  -c, --config <file>     config file (default: siftcode.config.json in the scanned folder)
      --baseline <file>   accept the findings listed in this baseline file
      --fail-on <level>   exit 1 if a finding is at least this severe: error, warning, info, note
```

Exit codes: `0` success, `1` a finding at or above `--fail-on`, `2` usage or configuration error.

`--format html` writes one self-contained file you can open in a browser or send to a colleague: a
summary, the top hotspots, filters (severity, category, language, rule, and a search), findings grouped
by file with why each matters and what to try, copyable before and after examples, a light and dark
theme, and (i) buttons that explain the terms. It loads nothing from the network, and it carries no
timestamps or absolute paths ([ADR 0012](docs/adr/0012-html-report.md)).

Upload results to GitHub code scanning with `--format sarif`. `--format json` also includes the
measurements of every file and function: cyclomatic complexity, Halstead measures, Maintainability
Index, lines of code, nesting depth, and parameter count (how they are defined:
[ADR 0005](docs/adr/0005-metric-definitions.md)).

## Accepting findings you have decided to live with

A tool that cannot be told "not this one, and here is why" gets switched off. SiftCode has two ways to
accept a finding. Accepted findings are never counted toward `--fail-on`, and the reports say how many
were set aside and how (the JSON and SARIF reports list them).

**A comment in the code, for one finding, with the reason.** Put it on the line the finding starts on, or
alone on the line above:

```js
// siftcode-ignore SC-MET-001: legacy parser, rewrite tracked in #42
function parse(input) {
```

```python
# siftcode-ignore SC-MET-002, SC-MET-004: state machine, split would hide the transitions
def next_state(event):
```

`siftcode-ignore-file SC-MET-006: generated by a tool` anywhere in a file accepts that rule for the whole
file. Both the rule id and a reason are required: a comment without either does nothing, and the report's
notes say so. A comment that matches no finding is also reported, so stale ones get cleaned up. Work
that belongs to a whole project (a missing license, a missing CI file) has no line to comment on; use
the baseline or switch the rule off in the config.

**A baseline file, for everything that is there today.** Adopting a new tool on an old codebase should
not mean fixing everything first:

```text
siftcode baseline .                    # writes siftcode-baseline.json
siftcode scan . --baseline siftcode-baseline.json --fail-on warning
```

Findings in the file are accepted; new ones are reported and fail the build. Commit the file. It holds
no dates and no absolute paths, sorted so a diff shows what changed. A finding is matched by rule, file,
and what was flagged, not by line number, so moving code does not bring it back (renaming the file
does). When a finding is fixed, the scan says the baseline lists something that no longer occurs; run
`siftcode baseline` again to refresh it. Put `"baseline": "siftcode-baseline.json"` in the config to
use it without the flag. Decisions: [ADR 0011](docs/adr/0011-baseline-and-suppressions.md).

The security rules (`SC-SEC-*`) look for well-known risky patterns in the syntax; they cannot tell
whether a value comes from an untrusted source, so they report at `warning`, skip test code, and
never print a credential they find (only where it is). SARIF output carries the CWE as the
`external/cwe/...` tag that GitHub code scanning displays. TypeScript declaration files (`.d.ts`)
are skipped.

The supply-chain and documentation rules (`SC-SUP-*`, `SC-DOC-*`) read the project's files instead
of its code: package manifests (`package.json`, `requirements*.txt`, `pyproject.toml`, `Pipfile`,
`*.csproj`), lockfiles, CI configuration, Markdown, and diagram files. The manifest checks
(`SC-SUP-001` to `003`) run on every manifest found; the rest only run when you scan the top of a
Git repository (a folder holding `.git`), because scanning a subfolder cannot tell whether the
project as a whole has CI or documentation. Design documentation is found by file and folder names
and fenced diagram blocks (Mermaid, PlantUML, D2, draw.io, ADRs, C4, OpenAPI, and more); see
[ADR 0008](docs/adr/0008-repository-hygiene.md). `SC-SUP-006` and `SC-SUP-007` cannot see settings
kept on the hosting platform (such as GitHub secret scanning); switch a rule off with
`"SC-SUP-007": { "enabled": false }`.

The testing and resilience hints (`SC-TST-*`, `SC-RES-*`) are suggestions, not defects, and are
reported at information or note level (a project with no tests at all is a warning once it has 20 source
files). They look at files and dependency manifests, and for calls at the syntax: `SC-RES-001`, the one
with a known failure mode (`requests` has no default timeout, so a slow server hangs the caller), stays
quiet when a timeout may be supplied where it cannot see (`**kwargs`, a configured client), and ignores
same-origin and localhost requests. `SC-TST-002` fires on most projects (they have example tests and
nothing else); switch it off with `"SC-TST-002": { "enabled": false }` if it is not useful. Decisions and
evidence: [ADR 0014](docs/adr/0014-release-pipeline-and-readiness-rules.md).

`SC-DOC-006` reads files only: it takes the source file paths a design document names in inline code and
links (not in code blocks, and not placeholders or patterns) and reports the document when at least two of
them are not in the project, for example after files were renamed or removed. It is a firmer sign of an
out-of-date document than how much code changed ([ADR 0013](docs/adr/0013-real-world-calibration.md)).

The Git rules (`SC-HOT-001` hotspots, `SC-DOC-005` stale design documents) read the project's history
by running your `git` program, read-only and without running anything the project configures (see
[ADR 0010](docs/adr/0010-git-history-rules.md)). A hotspot is a file that is both complex (total
cyclomatic complexity) and changed in many commits in the last 12 months, ranked by the two multiplied.
In a folder that is not in a Git repository, or without `git` installed, both rules are skipped and the
report says so under **Notes**; nothing fails. Findings from these rules depend on the date of the scan
as well as the code.

The license rules (`SC-LIC-*`) identify the project's license from its `LICENSE` file (by comparing
the text with the bundled SPDX list; modified and custom licenses are told apart from standard
ones) and from `package.json`, `pyproject.toml`, and `.csproj` declarations, and check the two agree.
They read each dependency's license offline, from the npm lockfile, installed `node_modules`, a
Python virtual environment, or restored NuGet packages, and compare it with the project's using a
cited, versioned compatibility table. A dependency whose license cannot be found is reported as
unknown, never guessed. These are heuristic checks that point out gaps you may not have thought of.
`SC-LIC-001` to `006` only run at the top of a Git repository; see
[ADR 0009](docs/adr/0009-license-checks.md) for how licenses are matched, what the table covers, and
its limits.

The design rules (`SC-DES-*`) are heuristics: they read the shape of the code, not its types, so
they skip test code and a few idioms (see [ADR 0006](docs/adr/0006-design-heuristics.md)) and report
at `info` with low confidence. `SC-DES-001` also needs a method call in the chain by default, so the
example `user.getAccount().getSubscription().cancel()` (3 members) is caught with `maxChain: 2`.

`SC-DOC-007` and `SC-DOC-008` compare the diagrams in your design documents with the code. They read Mermaid
flowcharts and C4, and PlantUML components, in diagram files and in the diagrams of an architecture or design
document (not in tutorials or tests). A box is read as a claim about the code only when it is written like a module
name (`cli: args, exit codes`, `core/scan`, `Catalog.API`, `OrderService`); free text such as `Developer / CI` is a
description and is left alone. A claim is found when the project has a folder, file, project, package, namespace,
class, imported module, or dependency of that name, or writes a qualified name such as `chrome.storage.local` in its
code. Evidence and limits: [ADR 0017](docs/adr/0017-diagram-drift-rules.md).

The accessibility rules (`SC-WEB-*`) read JSX in `.jsx`, `.tsx`, and `.js` files, from the markup alone: they find
what is certain without running the page (an image with no `alt`, an empty button, a click handler on a `div`), and
they skip an element that spreads props (`{...props}`), because the missing attribute may be in them. They cannot see
a label written in another component, a design-system component, or anything about contrast or layout, so they
complement a browser check such as axe; they do not replace it. HTML files, Vue, and Svelte are not read. Evidence:
[ADR 0016](docs/adr/0016-accessibility-rules.md).

The architecture rules (`SC-ARC-*`) work from the imports between your own files. `SC-ARC-001` needs no
setup: it groups files into components (the folders under the folder that holds most of the code, or a C#
project's folders), and reports groups of components that import each other in a cycle, with the shortest
cycle and the imports that make it. `SC-ARC-002` checks a layering you declare, and reports nothing without it:

```json
{
  "rules": {
    "SC-ARC-002": {
      "options": {
        "layers": [
          { "name": "domain", "paths": ["src/domain/"], "mayImport": [] },
          { "name": "application", "paths": ["src/application/"], "mayImport": ["domain"] },
          { "name": "infrastructure", "paths": ["src/infrastructure/"], "mayImport": ["domain", "application"] }
        ]
      }
    }
  }
}
```

`paths` are gitignore-style patterns; a file belongs to the first layer that matches, a file in no layer is left
alone, and a layer may always import itself. Only imports that resolve to a file in the project count: a package,
the standard library, a `tsconfig` path alias, and a C# namespace that several projects declare do not. Details and
evidence: [ADR 0015](docs/adr/0015-architecture-rules.md).

## AI suggestions (optional, off by default)

A finding comes with the rule's general advice. If you have an AI service, `siftcode scan --ai` asks it for a
suggestion fitted to the code around each of the most severe findings, and shows it under the finding in every
format (text, Markdown, HTML, JSON as `aiSuggestion`, SARIF as a property), marked as written by a model and not
reviewed. Without `--ai` nothing is sent anywhere, and a scan never uses the network.

Add an `ai` section to `siftcode.config.json`:

```json
{
  "ai": {
    "provider": "openai",
    "model": "gpt-4.1-mini",
    "minSeverity": "warning",
    "maxFindings": 10
  }
}
```

- `provider`: `openai` for any service that speaks the OpenAI chat completions API (OpenAI, Azure OpenAI, Ollama,
  LM Studio, vLLM, OpenRouter), or `anthropic`. `model` is required: there is no default, because models change.
- `endpoint`: the service's base URL; the default is the provider's own. A service on another machine must use
  `https`; plain `http` is accepted for `localhost` only. For a local model (Ollama: `http://localhost:11434/v1`)
  no code leaves your machine and no key is needed.
- The API key comes from an environment variable only (`OPENAI_API_KEY` or `ANTHROPIC_API_KEY`, or the name in
  `apiKeyEnv`), never from the config file, and it is never printed.
- `minSeverity` (default `warning`), `maxFindings` (10, most severe first), `contextLines` (6 lines above and below
  the finding), `timeoutSeconds` (60), and `skipRules` (rule ids never sent).

What is sent, and what is not: before anything is sent, SiftCode prints how many excerpts, how many lines, from how
many files, to which host. Each excerpt is the lines around one finding, with the rule's explanation. Findings about
credentials (`SC-SEC-001`) are never sent, and every excerpt has anything that looks like a credential replaced by
`[redacted]` (key formats, URL passwords, a value given to `password` or `apiKey`, a long generated string). Nothing
else in the project is read or sent. The answer is shown as text, never as markup. A service that is down or refuses
the key leaves the findings as they were, says so in the notes, and does not change the exit code. Details and what
was and was not verified: [ADR 0018](docs/adr/0018-optional-ai-suggestions.md).

## Configuration

Optional `siftcode.config.json` in the scanned folder. Unknown keys are rejected so typos are caught.

```json
{
  "ignore": ["generated/", "*.min.js"],
  "rules": {
    "SC-MET-001": { "severity": "warning", "options": { "maxLines": 80 } }
  },
  "failOn": "warning"
}
```

- `ignore`: gitignore-style patterns, added to the built-in ignores (`node_modules`, `bin`, `obj`,
  `dist`, `build`, minified files such as `*.min.js`, ...) and the project's `.gitignore`. A pattern like
  `!bin/` or `!*.min.js` brings one back.
- Generated files are read but not analyzed: a file whose first lines say a tool wrote it (`<auto-generated>`,
  `@generated`, "Generated by the protocol buffer compiler", "Code generated ... DO NOT EDIT") gets no rule run on it,
  because a finding there cannot be acted on. The report's notes say how many files were left out.
- `rules`: per rule id, `enabled` (default `true`), `severity`, and rule-specific `options`.
- `failOn`: same as `--fail-on`; the flag wins.
- `baseline`: path of a baseline file, relative to the scanned folder; the `--baseline` flag wins.
- `ai`: the AI service for `--ai` (below). Does nothing without the flag.

## Project structure

```text
src/
  cli/         commands (scan, baseline, explain), argument handling, exit codes
  config/      config file schema and loading
  core/        scan pipeline, findings, severity, errors
  discovery/   finding supported files; .gitignore and ignore patterns
  languages/   language registry, tree-sitter parser, Code Model, function extraction
  reporters/   text, JSON, Markdown, SARIF, HTML (html/), and `explain` output
  rules/       one file per rule, plus the registry
assets/        the HTML report: brand/ (from `brandkit bundle`, never edited by hand) and report/ (its own styles and script)
scripts/       build helpers, SARIF schema download, benchmark
test/          unit tests, end-to-end tests, fixtures
docs/          product and engineering documentation
```
